## 1. Purpose

CWS OS is the private operating system for Cicero Web Studio, run by one owner.

It exists to answer one question every day: **what is the best next move for the business, and is it done?**

It does this by keeping the business's real state in one place (sales, marketing, delivery, money, obligations). It derives priorities from that state. Laya evaluates each priority. And the system lets the owner carry out external actions (posting, emailing) safely, one confirmed action at a time.

It is not a generic project-management tool, CRM, or AI chat.

**In one line:** CEO Today decides the order. Laya evaluates each item. The owner confirms.

## 1a. Current strategy

- **Primary offer:** Negocio Listo, a subscription with a $300 setup fee and a 12-month term.
- **Goal:** 10 active subscriptions by 2026-12-31.
- **Checkpoint:** at least 4 signed by 2026-11-15.

The strategy is approved product context. Recording it as an active business decision (§3b) requires a separate owner activation; DECISIONS-001 preserves the existing legacy proposal without activating it.

Goal pace implementation: CEO Today pins these approved targets above the action list and derives Chicago calendar days to each deadline. The owner records signature status/date, subscription status with its verification date, source/reason and core-subscription inclusion for each Negocio Listo agreement. Corrections append history. A separate owner completeness check confirms the full register, including missing agreements and explicit exclusions; its snapshot is generated by the database and must match the exact register/date the owner reviewed. Count one core subscription per client and explicitly exclude add-ons/replaced agreements. Numeric signed-by-checkpoint and current active counts are used only when all included evidence is known, statuses were checked today, and the owner confirmed the exact complete register today. Changes or a new Chicago date invalidate completeness. Empty records remain unknown until explicitly confirmed complete. Failed/truncated reads produce needs_data. Counts and remaining gaps are evidence, not an on-track forecast; no weekly rate is inferred without a baseline. Recording subscription evidence does not modify a provider subscription or activate a business decision.

## 2. What is live

The admin app (`/admin`) has six surfaces. These are the product.

Shows Negocio Listo lifecycle items, decision-review items, a pinned Goal pace line, and a Laya verdict on each item. Laya never changes the order. | reads from all departments, plus `business_decisions` |

`agent_runs` is live shared infrastructure. It records AI PREPARE runs: creative drafts and prospect briefs.

The Negocio Listo landing pages (`/negocio-listo`, `/en/negocio-listo`) capture leads through `POST /api/outreach/public-lead`, which inserts or merges one `inbound` `leads` row owned by the workspace owner and triggers no external action.

Owner-controlled test leads: an authenticated active workspace owner may toggle `leads.is_test` with a required classification reason. The database records the actor/time and rejects member/service-role classification or forged provenance. Default is live; names/source text never auto-classify existing rows. Sales provides a separate owner control listing excluded leads and restoring them. Test leads do not contribute Sales priorities (including promises), progress or unclassified counts, CEO Today priorities, or live Negocio Listo lifecycle/deal-fit advice. This is a lead-only classification: it does not infer or alter any agreement's identity, finances, provider state, decision activation or existing sends/promises/saved Laya history. It is not a global send prohibition; existing exact-draft confirmation remains required elsewhere.

## 3. Authority model

| Tier | Meaning | Examples |
| --- | --- | --- |
| **AUTO** | Reads, derives, and displays. Never changes business data or the outside world. | CEO Today ordering, lifecycle stages, Laya evaluations, missed-slot detection, Day 0/4/10 state |
| **PREPARE** | Creates drafts, proposals, or internal records the owner will review. Nothing leaves the system. | Creative drafts, email drafts, prospect briefs, business-decision candidates |
| **CONFIRM** | Any external mutation. It requires a short-lived, single-use owner confirmation bound to the **exact** resource (slot + asset, or lead + recipient + draft). Every action is recorded before and after it reaches the provider. | Publishing a post, sending an email |

Rules:

- **AI may AUTO and PREPARE. It never CONFIRMs.** There is no AI execute tier. "Auto" in any proposal means AUTO as defined here, which is read-only.
- Reloads, GETs, reconciliation, and "Not now" actions can never trigger a CONFIRM action.
- Time-based state is derived, never stored. Only the owner's decision or response is persisted (DEC-029).
- **Confirmation ≠ approval.** A *confirmation* is the owner authorizing one exact external action, and it is always a gate. There is no separate approval gate in the solo-operator model.
- AI must never invent metrics, contact leads, spend money, publish, or change goals on its own.

Commercial email includes the owner-configured postal address, marketing disclosure, and recipient opt-out link in the exact draft the owner reviews. Workspace/email opt-outs persist across Sales, mailing lists, and duplicate records. Recipients record opt-outs by POST from the public unsubscribe page; GET and reload never change preferences. The owner can record opt-outs received by reply.

## 3a. Laya — the evaluator

Laya is the advisory evaluator. It is not the name of the assistant or of the OS.

- Every Laya evaluator returns the same contract:
  - `evaluator`
  - `policy_version`
  - `subject`
  - `verdict` (`do` / `revise` / `hold` / `skip` / `needs_data`)
  - `next_action`
  - `why[]`, where each item is a claim plus its source row
  - `assumptions[]`
  - `missing_data[]`
  - `money_at_stake` (from data only, or null)
  - `related_decisions[]`
- **Rules set the verdict.** v1 evaluators are deterministic code:
  - `lifecycle`
  - `deal_fit` ($50/h floor, setup fee, capacity)
  - `goal_pace`
  - `decision_review`
- LAYA-001 implements read-only `decision_review` evaluations in CEO Today through its existing GET: rules return the shared contract, cite the decision row and exact field values, and expose the Chicago evaluation date. Missing/invalid review data returns `needs_data`; due active reviews return `do`; future reviews and complete proposals return `hold`; closed decisions return `skip`. Free-text conditions still require owner observation. It adds no LLM call, decision mutation, or new endpoint. Owner responses are implemented as follows.
- DEAL-FIT-001 derives source-backed deal-fit advice outside priority ordering. Owner-JWT-only `negocio_listo_deal_budgets` now records full setup labor, recurring labor/month, setup direct costs and recurring direct costs/month, a future/current capacity window, available work hours, other committed hours excluding this deal and this deal’s demand in that window. Hours are whole numbers and costs integer cents; zero costs must be explicit. Owner completeness declarations and a source/correction reason are required. Evidence is append-only; no actual time, costs, payment or provider state is changed.
- Budgeted hourly fit compares `(setup + monthly × term − setup costs − monthly costs × term)` against `$50 × (setup hours + monthly hours × term)` without rounding. The setup quote must meet $300. Capacity compares this deal’s window demand with available minus other committed hours, only for the reviewed dates. All meet → `do` (advisory); setup/economic shortfall → `revise`; insufficient capacity → `hold`; missing, stale, failed or truncated evidence → `needs_data`. These are owner estimates, not realized profit, deal acceptance or a capacity reservation.
- Completeness binds to the exact displayed agreement prices, other recorded deal-plan content, project versions/links/hours and recorded project costs, checked by the database on the current Chicago date. Changed sources or the next day require review again. One same-client project must be linked; full budgets cannot be below hours/costs already recorded. Capacity availability cannot exceed the calendar window’s hours; window demand must fit full-term labor. The owner explicitly reconciles all commitments, including non-Negocio Listo/off-system work; the app does not infer completeness from project counts. Identical other-deal re-reviews do not invalidate each other. No LLM, provider action, decision activation or new endpoint is introduced.
- After the gate (§9a), an LLM may only write the `why` text and drafts, using the same snapshot. It never sets or changes a verdict.
- A claim without a source is a bug. Missing data produces `needs_data`, never a guess.
- Evaluations are computed live (AUTO). Only an explicit owner Act/Dismiss save with a reason writes `laya_evaluations`, preserving the exact reviewed input snapshot, evaluation, authenticated actor, response, reason and timestamp. Opening/canceling a form, GET and reload never write. Act records intent to follow the advice; it does not perform the advice, activate/edit a decision, dismiss a decision, or change priorities.
- The existing CEO Today route verifies active ownership and a 15-minute signed review bound to that owner/workspace and exact snapshot/evaluation. Owner-only Act/Dismiss responses cover decision reviews, the pinned goal pace evaluation and individual lead/agreement deal-fit and lifecycle evaluations. Goal/deal responses preserve the actual evaluator inputs (including availability flags, clock, prices, source evidence, budgets and capacity snapshot) and the exact output displayed; they never reload current facts and substitute them for reviewed evidence. Subject metadata is derived from the saved evaluation; decision linkage remains exclusive to decision reviews. Legacy decision tokens/history remain supported. Oversized evidence withholds response controls rather than truncating inputs. Opening/canceling forms does not save; refreshed review tokens reset the goal/deal forms, and submitting retains the token opened. History shows the latest30 workspace responses, filtered by evaluator/subject, with the complete saved snapshot/output available to the owner. History is append-only, owner-readable, and accepts identical retries once. A later change to the decision does not rewrite the reviewed evidence; the response describes the signed snapshot, not an inferred current state.
- CEO Today includes a unified owner-only Laya response history, filterable by Decision, Goal pace, Deal fit and Lifecycle, Act/Dismiss, and saved-response date range. It pages through all saved workspace responses newest first, 30 per page, including saved reasons and expandable exact snapshots/evaluations even when the subject is absent from current review cards. Type, response, date and saved-text search combine on the server across the full history and reset to page one. Search history applies up to 80 characters of case-insensitive literal text to saved reasons, subject IDs/types, decision titles/text, lead names/companies and agreement product names. It searches saved evidence only, never current source records. Search drafts apply explicitly; blank search removes only the search criterion. Clear filters also clears search. Dates are inclusive Chicago calendar days based on response created_at, with either bound optional and daylight-saving boundaries respected. Dates require Apply dates; Clear filters resets all criteria. Applied criteria are shown with the page. Older/Newer controls use timestamp-and-ID cursors and retain visited newer pages; new inserts do not shift older-page boundaries. Every page read verifies active ownership and workspace scope; cursors bind all applied criteria. Failed reads keep the displayed page and offer retry. Refresh resets the view; history reads and filters perform no business action.
- LAYA-LIFECYCLE-001 adds deterministic `lifecycle-v1` evaluations to existing Negocio Listo cards without changing stage derivation or priority ordering. Recorded inquiries, setup/due/overdue payments, CWS delivery work, completed delivery awaiting a launch record and term-end review return `do`; waiting on client, paused work and a recorded launched agreement return `hold`. Missing/truncated/unavailable reads, invalid prices/term/launch dates, duplicate billing links, incomplete launched schedules, inconsistent/void/non-USD obligations, invalid receipts or unsafe totals return `needs_data`. These are prompts to review source records, never permission to charge, launch, follow up or renew.
- Lifecycle evaluations cite exact same-workspace principal and explicitly linked source rows with fields/version and Chicago clock. Owner Act/Dismiss uses the same signed15-minute response path, preserving the actual scoped evaluator inputs, availability, full evaluation, response/reason/actor/time. A matching lead or agreement must still exist in the workspace; the snapshot must identify Negocio Listo. Historical evidence is not replaced with later records. Oversized snapshots withhold saving instead of truncation. Lifecycle is included in existing history type/date/response/search filters and pagination. Activation remains separate.
- To add a capability, add one evaluator and its fixtures. Do not add a new engine, agent, or endpoint. All of Laya is served through one route.

## 3b. Business decisions

- Business decisions live in `business_decisions`, reshaped from the v1 `decisions` table.
- Statuses: `proposed`, `active`, `superseded`, `rejected`. **A decision binds only when it is `active`, and only the owner sets `active`.**
- Every active decision has a `review_by` date and a `revisit_condition`. When either one fires, CEO Today shows a review item (derived).
- DECISIONS-001 derives date reviews in Chicago time and displays them separately from the unchanged department priority order. Free-text revisit conditions are owner-assessed: the owner records or clears an observation that the condition occurred; the app derives a review from that evidence. It does not guess whether arbitrary conditions are true.
- Activation is an explicit owner action after reviewing the exact decision, date, and condition. The database records the authenticated actor and timestamp; PREPARE/service-role writes cannot activate or update decisions. Active terms are immutable; the owner may reschedule reviews or supersede the decision.
- AI may PREPARE `proposed` candidates from a conversation. Nothing is auto-saved from chat.
- Architecture decisions stay in `docs/decisions.md` (DEC-012).

## 3c. Negocio Listo lifecycle and project hours (LIFECYCLE-001)

- CEO Today derives lifecycle items from explicit `negocio-listo|…` inquiry tags and `Negocio Listo` agreement product snapshots. Agreement creation is not evidence of signature; client names are never used to infer conversion or project linkage.
- Stages cover prospect, setup payment pending/overdue, missing linkage/data, delivery/waiting/paused, launch-record pending, recorded launch, installment due/overdue, and term completed. Dates use Chicago time. A provider reference is not proof of payment or live subscription state. Stages are never saved automatically.
- The owner explicitly links an Operations project to an agreement belonging to the same workspace and client. Missing or multiple project links require review. Launch and payments continue through existing owner-controlled Accounting records; lifecycle GET never creates bills, launches, charges or messages.
- Lifecycle evidence appears in CEO Today and is included in existing deterministic priority tiers. Inquiry cards enrich the Sales queue without duplication, preserving Sales ordering. A linked delivery/payment item replaces its matching generic card. No new scoring or LLM evaluator is introduced in this milestone; the remaining Laya evaluators/goal pace remain separately scoped.
- `project_time_entries.hours` is an owner-entered positive integer, with work date and optional notes. Fractions are rejected rather than rounded. Only an authenticated owner can add/correct/remove entries; the service role can read but cannot invent time. Corrections preserve entry identity/provenance; removal requires an explicit UI action.
- Project `actual_hours` is a guarded cache of the entry sum for existing financial views and hourly rates. It cannot be written directly. A private owner-checked trigger synchronizes totals; per-project writes are serialized. Removing the last entry restores unknown hours, not an invented zero. Existing production totals were unset; no history was backfilled.

## 4. Product principles

Favor:

- **Live, observable outcomes over capability.** A feature is done when its real-world metric moves: posts published, emails delivered, payments recorded, subscriptions signed.
- **One department surface per business function.** Don't add a new top-level surface without a decision.
- **Deterministic logic** before scoring, weights, or AI ranking.
- **Small, frozen milestones.** Ship, verify live, freeze, and only then scope the next one.
- **Structured data, traceable history, append-only evidence.**
- **Solo-operator usability:** nothing waits on a second person.

Avoid:

- Generic task, approval, workflow, event, or CRM frameworks.
- Autonomous strategy changes or recursive agent loops.
- Building above a layer whose real-world metric is still zero.

## 9. Not building now

- Unconfirmed or scheduled auto-publishing and auto-sending
- An AI execute tier of any kind
- A separate CEO engine, multi-agent departments, or a central AI that reorders priorities
- Automatic learning loops, policy-versioning infrastructure, and recursive self-improvement (data is captured in `laya_evaluations`; behavior waits)
- Auto-saving decisions from chat
- Client portal (disabled until separately scoped)
- Full CRM, team/multi-user complexity, generic workflow or approval engines
- Ranking weights or AI scoring in CEO Today
- Video rendering, Final Cut Pro automation

## 9a. Gate for in-app AI

The existing advisory Marketing draft assessment (`/api/laya-assess` and the Marketing assessment flow) is grandfathered; it remains advisory and cannot approve or publish. The gate below applies to new in-app AI features.

No new in-app LLM call (`LAYA-BRIEF-001` or anything like it) until both of these are true:

- At least 3 clients have moved through the Negocio Listo lifecycle.
- Sales has run at the DEC-031 rate for 4 consecutive weeks.

Until then, strategy conversation happens in the Claude Project.

## 10. Definition of done (every ticket)

1. Merged to `main`. Production deploys from `main`.
2. Every applied migration has a committed file whose version **exactly matches** the remote version.
3. One task-ledger row plus the agent's handoff file updated.
4. Live verification recorded, read-only where possible.
5. If the ticket changes scope or authority, this document is updated in the same PR.
6. Any new Laya evaluator ships with fixture scenarios, and CI fails on verdict regressions.
